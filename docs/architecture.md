# Architecture

Across Amazon is a Manifest V3 extension with five parts:

- **Popup** (`popup.html`, `src/popup`): a React app that shows one comparison for the active tab.
- **Background service worker** (`src/background`): runs comparisons, sends each target store page to the offscreen document as a page job, owns the fallback tabs, fetches exchange rates and caches results.
- **Offscreen document** (`offscreen.html`, `src/offscreen`): downloads the other stores' product and search pages and reads them, without a tab. It is bundled by its own Vite build.
- **Content scripts** (`src/content`): three small extractors and the delivery location setter, injected on demand with `chrome.scripting.executeScript` into the active tab and into the fallback tabs the worker opens when a page cannot be read in the offscreen document. None is declared in the manifest, so nothing runs on a page until a comparison asks for it. The offscreen document imports the same modules.
- **Options page** (`options.html`, `src/options`): the full settings form.

The manifest asks for `offscreen`, `scripting` and `storage`, plus host permissions for the ten Amazon domains and the two exchange rate hosts, `www.ecb.europa.eu` and `api.frankfurter.dev`. Without `tabs`, Chrome gives the popup the active tab's URL only on those Amazon hosts, so any other tab reads as not on Amazon. `offscreen` lets the worker open one offscreen document with the reason `DOM_PARSER`; Chrome shows no install warning for it. Setting a store's delivery location and reading its other sellers' offers need no other permission: those requests go from the offscreen document to the store under its host permission, with the user's cookies, or from the store's own page to its own origin in a fallback tab.

### 1. The popup opens

The popup asks `chrome.tabs.query` for the active tab. If the URL's host is not one of the ten marketplace domains, it shows "Open an Amazon product page" and sends nothing to the background.

Otherwise it sends `LOAD_SOURCE` with the tab id. The background (`loadSource` in `orchestrator.ts`) injects `content/source-extractor.js` into the tab to read the **source context**: marketplace, ASIN, title, brand (from the brand row of the product overview, else the store byline), variation tokens from the selected colour, size, style and pack options, the destination country as an ISO 3166-1 alpha-2 code and the text of Amazon's "Deliver to" box, and the product image. The destination comes from fields Amazon renders on the page for its own scripts, in this order: the `vas-base-vm` state block's `countryCode`, the hidden `input#countryCode`, then the inline `$Nav.declare('config.customerCountryCode', …)`; a `null` there means unknown. Without them it falls back to the country named in the "Deliver to" box, then to the marketplace's own country when the box shows a town and a postcode in that marketplace's format. Otherwise the destination is left unset; it never defaults to the marketplace's country. The United Kingdom is `GB`. It then injects `content/product-extractor.js` into the same tab to read the **baseline**: item price, shipping and import fees on the page you are on. `LOAD_SOURCE` returns the raw baseline without fetching exchange rates, so the idle view appears quickly. If the source context cannot be read, the response carries an `error` and the popup shows the not-on-Amazon notice. If only the price cannot be read, the popup shows the product without one.

### 2. The user starts a run

Clicking the button creates a **run id** (`crypto.randomUUID()`) and sends `RUN_COMPARISON {activeTabId, runId}`. The popup switches to the running view straight away.

The background (`runComparison`) then:

1. **Registers a run token** for the tab. A token holds a key (`crypto.randomUUID()`) that names the run's page jobs, a `cancelled` flag, an abort controller, whether the run sent a page job to the offscreen document, the ids of the fallback tabs it opened and the delivery location result of each target marketplace. Starting a run for a tab cancels any previous token for that tab.
2. **Extracts the source context** again on the active tab and **loads the settings** (`settings:v1`). The target marketplaces are the enabled ones minus the source marketplace.
3. **Checks the cache.** The key (`cmp:<hash>`) is built from a cache version, the ASIN, variation tokens, source marketplace, destination country, the source page's "Deliver to" text and target marketplaces. The text keeps two addresses apart that resolve to the same country code, such as a town and postcode and the bare country. A record younger than 30 minutes is returned as the result immediately, with no progress messages, no downloads and no tabs. The version changes when extraction or matching changes, so a result cached by an earlier build is never shown. It is 8 since a robot check ends a marketplace and a run with one is not cached.
4. **Extracts the baseline and fetches the FX table** at the same time; no marketplace is read before both are done. The baseline is read on the active tab. Missing shipping or import fees on the page you are on count as zero, except the import fees of a baseline quoted from [another seller's offer](#other-sellers-offers), which stay unread so the popup says the page's total leaves them out. The FX table (`fx-service.ts`) is stored per UTC day as `fx:YYYY-MM-DD`. When today's table is missing, the worker fetches the ECB daily reference rates XML and falls back to the Frankfurter API (`api.frankfurter.dev/v1/latest`). Both rate hosts are host permissions: the ECB feed sends no CORS headers, and listing Frankfurter keeps the fallback independent of its CORS headers. If both fail the run ends with an error, with the raw baseline and no FX table.
5. **Checks the target marketplaces three at a time** (`MARKET_CONCURRENCY` in `src/shared/markets.ts`), each marketplace's pages one after another, so within a check no store has two of the extension's requests in flight; two checks on two tabs can overlap. Every page goes through `readPage`, which downloads and reads it in the offscreen document and reads it in an inactive fallback tab only when it cannot be read that way (see [Reading a page](#reading-a-page)):
   - **OPEN**: reads `https://<domain>/dp/<source ASIN>` with the product extractor, setting the marketplace's [delivery location](#delivery-location) first when needed. The page is the source product when its own ASIN field or canonical link names the source ASIN, it has a product title, and that title shares at least one word with the source title. The marketplace is then **matched by ASIN**: it skips to READ with a match score of 1 and the note "Matched by ASIN". A not-found page (HTTP 404 on the download, read as no product without a tab or a location step), a redirect to another ASIN, an unrelated title or a failed read falls back to a **search**. So does a **dead listing**, a page for the source ASIN with no price that says the item is currently unavailable or out of stock (in English, German, French, Italian, Spanish or Japanese) or has no availability notice and no way to buy, as amazon.de and amazon.fr still serve the black WH-1000XM5; that search skips result cards for the source ASIN. A page with no price because the item cannot be shipped to the address is still matched by ASIN: the listing is live, and a search would find no better one on that marketplace. A robot check never falls back to a search: it ends the marketplace (see [Fallback tabs and robot checks](#fallback-tabs-and-robot-checks)). When the source title carries a distinctive model number (at least five characters with two letters and two digits that is not a measurement such as `128GB`, for example `WH-1000XM5`), the worker first reads `https://<domain>/s?k=<brand model>`: amazon.co.jp lists no WH-1000XM5 for the whole English title but lists it first for "Sony WH-1000XM5". When that search yields no confident match, or the title has no such model number, it searches `https://<domain>/s?k=<title brand variant>`.
   - **SEARCH** (search fallback only, once per query): reads up to eight organic result cards (ASIN, title, brand, price and product link, in both the current and the older card layout) with the search extractor. Sponsored cards and cards without a `/dp/` or `/gp/product/` link are skipped.
   - **MATCH** (search fallback only): scores every candidate against the source (`shared/matching.ts`). A candidate with the source ASIN and at least one title word in common scores 1. Any other candidate is scored on title token similarity 45%, brand 25% and variation 30%. Variation compares pack, size and colour tokens from the source's selected options and both titles. Brand only counts when the source page has one, and variation only when both the source and the candidate's title name one (search cards often leave the colour out of the title); the remaining weights are scaled up to 100%. A candidate without a brand gets 0.75 for brand when its title names the source brand. A candidate whose brand equals the source brand and whose title carries the source's distinctive model number scores its title at least 0.7, so a localized or reworded listing (amazon.it's "WH-1000XM5 Premium Bluetooth Headphones with Noise Cancelling", title similarity 0.545) reaches 0.8071; the lift is withheld from bundles (" & ", " + ", "bundle"), from candidates naming another colour, pack or size, and from candidates with a second model number. A candidate whose model numbers all differ from the source title's is capped at 0.5. Two model numbers are the same when they are equal once hyphens are dropped (`WH1000XM5` and `WH-1000XM5`) or when one is a bare segment of the other (`1000XM5`), so `WF-1000XM5` earbuds do not pass for `WH-1000XM5` headphones. The best candidate must score at least 0.78, otherwise the marketplace becomes `NO_CONFIDENT_MATCH`. The best candidate's product page is read next.
   - **READ**: for a search match, reads the cost stack with the product extractor and the source destination country. A match by ASIN uses the page already read during OPEN. A search match then gets a **variant check**: the values the page's twister has selected are compared with the source's colour, pack and size tokens, each kind on its own. When a kind conflicts (a silver listing for a black source), the worker reads the variant the page's twister offers with the source's attributes, once, instead, adding the note "Switched to the Black variant". When the twister offers no such variant, or that page still conflicts, the marketplace becomes `NO_CONFIDENT_MATCH` with the variant it found. When that page cannot be read, the worker keeps the listing it matched, with the notes "Could not read the Black variant: <reason>" and "Quoted listing is another variant: Silver"; when it is a robot check, the marketplace ends as one. The result is `DESTINATION_MISMATCH` when the page quotes another country than the source destination (its delivery location could not be set, or Amazon ignored the change), or when the location could not be set and the page shows no readable destination; `UNAVAILABLE` when the item price or the shipping is missing (including a page that exists but shows no price for the destination, whose notes relay Amazon's availability message), and `OK` otherwise. A page with no price that offers "See All Buying Options" is quoted from [another seller's offer](#other-sellers-offers) when one delivers there, so it is `OK` with that offer's item and delivery. The item price is the buy box's price to pay, else the centre column's: when its offscreen copy is blank, as it is in the centre column on every current layout, it is assembled from the visible currency symbol, whole and fraction. Per-unit, list (RRP), struck-through and twister prices are never read as the item price, and neither are other products' prices: the fallbacks that take any price to pay or any centred price look only inside the product block (`#ppd`), and the sponsored card above it, the recommendation carousels below it and the similar items of an out-of-stock box are always skipped, so a dead listing that suggests priced sponsored items stays unavailable. Shipping comes from amazon.com's AmazonGlobal details table, else its AmazonGlobal line ("No Import Charges & $17.88 Shipping to Switzerland"), else the price attribute of the primary delivery message (amazon.com's message text names only the date and the destination, and the fastest-delivery option is never quoted), else the text of the delivery blocks. Import fees come from the same table, then the same line, then the import blocks; "No Import Charges" or "No Import Fees Deposit" means zero import fees. When the line quotes one sum for both ("$76.32 Shipping & Import Charges to Switzerland"), the shipping is the delivery message's price and the import fees are the rest of the sum; when no delivery price in the same currency and at or below the sum is shown, the sum is the shipping and the import fees stay unread. A page that prices the item and the delivery but shows no import fees is `OK` with a total of item plus shipping and the note "Import fees not displayed for destination": only amazon.com shows import charges for an address abroad, in its AmazonGlobal details. The page's destination is read from the same page fields as the source's, first; without them it is the country named in its "Deliver to" box, or named in full in its delivery message or that message's destination attribute; two-letter codes count only in the box, so Spanish "de" or English "it" in a delivery message is not read as a country. When the box shows a town and a postcode in the marketplace's own format instead of a country, as Amazon does for an address at home (five digits for the US, Mexico and the EU stores, `A1A 1A1` for Canada, UK outward and inward codes, `123-4567` for Japan, four digits for Australia), the destination is the marketplace's own country (`GB` for amazon.co.uk), unless the source page's "Deliver to" box shows the same postcode. A page matches when its destination is unreadable, when the source destination is unknown, or when both codes are equal. Its confidence is 80% match score plus 20% parse confidence, so a fully read match by ASIN has confidence 1. Its notes start with "Matched by ASIN", or "Matched by search" and the confidence label, then the location step's note if any ("Delivery location set to Switzerland", "Delivery location not set: <reason>" or "Delivery location not offered: <code>"), and its link is `https://<domain>/dp/<matched ASIN>`. In a fallback tab the worker waits up to 25 seconds for the product extractor's result. An extractor that returns nothing, or any other thrown error after the lookup (a timeout, a closed tab, a script failure), becomes `PARSE_FAILED` for that marketplace only. Every fallback tab is closed as soon as its read ends, whether it succeeded or failed. The results are ranked in the order of the target marketplaces before they are sorted, so marketplaces with equal totals keep the settings order whichever finishes first.

   Each phase a marketplace enters sends `RUN_COMPARISON_PROGRESS` with `completed` (the marketplaces finished), `total`, `inFlight` (the marketplaces in progress with their phase, in target order, at most three), `latest` (the marketplace and phase that changed), the **partial ranking** of the results so far, and the FX table. A marketplace that finishes while others still run sends one without `latest`, and the last message has `completed = total` and an empty `inFlight`. Every message is a full snapshot. The popup uses them to draw the dial, the step line and the chips. A marketplace matched by ASIN reports OPEN then READ; a search fallback reports OPEN, SEARCH, MATCH and READ, with SEARCH and MATCH a second time when it also searches by title.
6. **Normalizes** each `OK` result. A quote from [other sellers' offers](#other-sellers-offers) first becomes the offer with the lowest delivered total in the comparison currency. Then the delivered total (item + shipping + import fees when the page shows them, in the page's currency, or Amazon's displayed total when it is higher) is converted to the comparison currency. When the charges are in different currencies, as for another seller's offer on amazon.co.uk with the item in pounds and the delivery to Switzerland in francs, each charge is converted on its own and the results are added; a displayed total, converted the same way, is kept when it is at least that sum, as for a total in one currency. A result whose total cannot be converted becomes `UNAVAILABLE` with the note "Missing FX conversion path to <currency>".
7. Sends a final progress message with `completed = total`, **writes the cache record** unless a marketplace ended with a robot check or the run hit its deadline, and returns the payload: source, baseline, sorted results, `generatedAt`, FX table, `activeTabId` and `runId`.
8. **Closes any fallback tabs** that are still open, whatever the outcome, then the offscreen document once no run is left. The worker also closes any offscreen document when it starts: one that is open then was left by a worker that stopped mid-run.

A run has 240 seconds (`RUN_DEADLINE_MS` in `src/shared/comparison.ts`) from its start. Chrome stops a service worker whose single request takes more than 5 minutes, and the held `RUN_COMPARISON` response is that request. When the deadline passes, the run is cancelled as Stop would cancel it, every marketplace not finished by then becomes `PARSE_FAILED` with the note "Timed out after 240 seconds", which the popup shows as "The check ran out of time before this store was read.", and the run is not cached.

The service worker (`service-worker.ts`) sends the payload as `RUN_COMPARISON_RESULT` and only then answers the original `RUN_COMPARISON` message with `{ok: true}`. If the popup gets no `ok` answer (the background could not be reached), it ends the run with "Could not reach the background service".

The popup ranks and labels results itself (`src/popup/view-model.ts`). It converts every delivered total to the display currency from the result's own breakdown and the FX table, so changing the display currency never needs a new run. A result whose charges are in different currencies is converted charge by charge, and its total in the store's own currency (the ranked row and the breakdown sheet) converts the other charges into the item's currency; without an FX table that total shows "—".

### Reading a page

Every product and search page of a target marketplace goes through `readPage` in `orchestrator.ts`. When Chrome has `chrome.offscreen` (version 109 and later), it sends the page to the offscreen document as a page job. `runPageJob` in `src/background/offscreen-client.ts` creates the one document (`offscreen.html`, reason `DOM_PARSER`) on first use, shared by the lanes, and counts Chrome's "Only a single offscreen document may be created." as a document already there, left by an earlier worker. It sends `OFFSCREEN_PAGE_JOB` with the run key, the URL, the page kind and its extraction request, a location request while the marketplace has no location result, and the source destination as the expected destination once the marketplace's location is `SET` or `ALREADY_SET`. `readPageJob` in `src/offscreen/page-reader.ts` then:

1. Refuses, without a download, a URL that is not `https:` on one of the ten stores (`off-host`): a search result card may link its product on another host or over plain HTTP. Otherwise downloads the page with `fetch(url, { credentials: "include" })`, so the request carries the user's Amazon cookies, with 15 seconds for the answer and its body.
2. Takes the final URL after redirects and refuses one on another host than the requested store's (`off-host`). Only a redirect to another Amazon store can get that far: a redirect to any host outside the host permissions fails the download as a network error.
3. Decodes the bytes in the charset the `Content-Type` header names, else the one a `<meta>` names in the first 1024 bytes, else UTF-8, and refuses a charset `TextDecoder` does not know (`charset`).
4. Judges the page with `isRobotCheck` on its final URL, HTML and status (`robot-check`), answers `not-found` for a product page served with HTTP 404, and refuses any other status that is not 2xx (`http-status`).
5. Parses the HTML with `DOMParser` into an inert document, with a `<base>` at the final URL so relative links resolve as they do on the page. None of Amazon's scripts run and no image, stylesheet, script or ad loads. A document without the marks of the page kind is refused (`shape`): for a product page `#productTitle`, `#ASIN`, an `ASIN` input or a canonical link, for a search page a result card, Amazon's results container or its result bar. This also catches the 12-element page amazon.co.uk once served instead of a product.
6. With an expected destination, refuses a page that shows another one (`destination`).
7. With a location request, runs `setDeliveryLocation` on the parsed document with the final origin and a fetch that sends the user's cookies, within 10 seconds. `SET` answers `location-set` without reading the page, which Amazon rendered for the old location.
8. Reads the page with the same `extractSearchCandidates` or `extractProductDataWithOffers` the content scripts run, with a fetch that forces `credentials: "include"`. A first All Offers request answered with a status that is not 2xx or with a robot check is refused (`offers`); a refused second or third page keeps what was read.
9. Answers a small JSON result: `read` (the candidates or the product, with the location result), `location-set`, `not-found`, `robot-check`, `cancelled`, or `fallback` with its reason.

The job ends after 25 seconds as a `timeout` fallback. On the worker's side, the document has 10 seconds to open (`OFFSCREEN_CREATE_TIMEOUT_MS`, which also covers waiting for a close in progress), and once the job is sent, 27 seconds to answer (`PAGE_JOB_ANSWER_TIMEOUT_MS`). Both end as a `no-answer` fallback, so the worker gives up only on a document that did not open, died or never answers, never on a job the document is still running. Stop and the close after the last run also wait at most 10 seconds for a creation in progress, and the close itself is given up after 10 seconds, so a creation or a close that never settles cannot hold back a run's result, the answer to Stop or the next run, which creates the document again. A send that fails or gets no answer means the document went away (its renderer crashed, or the extension's pages reloaded), and the next job creates it again.

`readPage` then acts on the result:

| Rule | Result | What the worker does |
| --- | --- | --- |
| F0 | `not-found` | Reads it as no product, without a tab and without the location step: the lookup misses and searches, a variant counts as not offered, and a search match ends `PARSE_FAILED` with "No product extraction data returned". The marketplace's next page carries the location request. |
| F1 | `robot-check` | Reads that page once in a fallback tab. When the tab shows a robot check too, the marketplace ends as one (see [Fallback tabs and robot checks](#fallback-tabs-and-robot-checks)); a clean read in the tab goes on as usual and the run stays cacheable. |
| F2 | `fallback` for a URL off the stores or a redirect to another host, a failed or slow download, an unknown charset or page shape, another HTTP status, an error in the job, the 25-second job limit, or a document that did not open or gave no answer | Reads that page in a fallback tab, which runs the location step itself while the marketplace has no result. A redirect to another store costs the most: the tab follows the same redirect, waits the full 20 seconds for a store page that never comes and fails with "Timed out waiting for tab <id> to load". |
| F3 | `read` whose location step is `FAILED` after a request was sent (Amazon answered an error status or carried no token, did not accept the change, the network failed or the 10 seconds ran out) | Redoes the location step once in a fallback tab on the same page. When that sets the location or finds it set, the page is downloaded again; otherwise the job's reading is used, and the job's `FAILED` is recorded when the tab recorded nothing. A robot check in that tab ends the marketplace as one. A `FAILED` before any request (a form on another origin, the store's own country) is recorded as it is. |
| F4 | `fallback` `destination` | Reads that page in a fallback tab, which only reads, because the location is recorded. It catches a download that sees another destination than a tab would, for example with third-party cookies blocked, on every page of the marketplace: the refetch after `SET`, the search after a lookup that missed, a search match and a variant. |
| F5 | `fallback` `offers` | Reads that product page again in a fallback tab, whose extractor requests the panel `same-origin` from the store's own page. |

A fallback records the location result it carries before the tab opens, except `NO_WIDGET` and a `FAILED` after a request, which the tab redoes; when the marketplace still has no result after that tab, the job's `FAILED` is recorded. `location-set` records `SET`, and the page is downloaded again with the destination expected. Any other `read` records its location result, except `NO_WIDGET`, and is used. A page gets at most two jobs, the first and one refetch after `SET`, because the refetch carries no location request; the page would be read in a tab if that ever broke. `cancelled` ends the marketplace with "Comparison cancelled by user". Without `chrome.offscreen` (Chrome before 109, which does not know the `offscreen` permission and installs the extension anyway), every page is read in a fallback tab.

| Limit | Where | Value | Then |
| --- | --- | --- | --- |
| Page download | offscreen | 15 s | read in a tab (F2) |
| Location step | offscreen | 10 s | `FAILED` "timed out after 10 seconds", redone in a tab (F3) |
| Other offers | extractor | 15 s | "Other offers could not be read: timed out after 15 seconds" |
| Page job | offscreen | 25 s | read in a tab (F2) |
| Document creation | worker | 10 s | read in a tab (F2) |
| Creation, for Stop and the close | worker | 10 s | the cancel is sent and the document closed anyway |
| Document close | worker | 10 s | given up; the next job creates the document or finds it open |
| Answer to a job | worker | 27 s from sending it | read in a tab (F2) |
| Page load | fallback tab | 20 s | "Timed out waiting for tab <id> to load" |
| Location step | fallback tab | 20 s | `FAILED` "timed out after 20 seconds" |
| Product read | fallback tab | 25 s | "Timed out reading the product page after 25 seconds" |
| Search read | fallback tab | 25 s | "Timed out reading the search page after 25 seconds" |
| Run | worker | 240 s from the run's start | unfinished marketplaces `PARSE_FAILED` "Timed out after 240 seconds", run not cached |

Chrome stops a service worker after 30 seconds without an event or an extension API call, and when one request takes more than 5 minutes; the held `RUN_COMPARISON` response is such a request, and the run deadline leaves a minute for the reads before the marketplaces and the cleanup after them. Page downloads run in the offscreen document, so Chrome's 30-second limit on a worker's `fetch()` answer does not apply to them; the worker fetches only the exchange rates. On the fetch path every wait of a lane ends within 37 seconds. On the tab path the page load, the location read, the product read and the search read are bounded, while `chrome.tabs.create`, the injections before the product and location reads and `chrome.tabs.remove` have no limit of their own: each is one API call that Chrome answers unless the tab's renderer hangs.

### Delivery location

The goal is the marketplace that delivers the item to the user at the lowest price, so every target marketplace must quote the source destination. When the source destination is known, every page `readPage` reads on a target marketplace carries a location request (`{marketplace, countryCode}`) until the marketplace has a location result other than `NO_WIDGET`. In the offscreen document the setter (`src/content/location-setter.ts`) runs on the parsed page with the page's final origin and a fetch that sends the user's cookies. Its requests come from the extension, not from a store page: Amazon sees `Sec-Fetch-Site: none` and no `Referer`, and the POST carries `Origin: chrome-extension://<id>`. In a fallback tab (`readTargetTab` in `orchestrator.ts`), the worker writes `__ACROSS_AMAZON_LOCATION_REQUEST__`, injects `content/location-setter.js` and awaits `__ACROSS_AMAZON_LOCATION_RESULT__` for up to 20 seconds, and the setter works from the page's own origin, with the store's cookies. Either way it:

1. It reads the page's destination with the same fields as the extractors. When it is already the destination, the result is `ALREADY_SET` and nothing is sent.
2. It reads the location widget, `#nav-global-location-data-modal-action`, whose `data-a-modal` JSON holds the form URL and the page token (`ajaxHeaders["anti-csrftoken-a2z"]`, else `#glowValidationToken`). A page without it (a not-found page) gives `NO_WIDGET`, which is not recorded, so the marketplace's next page tries again. A robot check never gets this far: a download that is one goes to a tab first, and a tab that shows one ends the marketplace before the setter is injected. A form URL on another origin than the page's is refused without a request (`FAILED`, "Amazon's location form is on another origin"), so the page token is only ever sent to the store itself.
3. A destination equal to the marketplace's own country is refused without a request (`FAILED`, "a postcode is needed for an address in the store's own country"): Amazon sets an address at home by postcode only.
4. It GETs the form URL (`/portal-migration/hz/glow/get-rendered-address-selections?…&storeContext=<ctx>&actionSource=desktop-modal`) with the page token in `anti-csrftoken-a2z`. Without that header Amazon answers a sign-in fragment with no token. The POST token is the `CSRF_TOKEN` of the form's `P.declare("GLUXWidget", …)` script, with its key and value in single or double quotes and the value's escapes resolved; a value with an escape it cannot resolve counts as no token. The page token and the form's `meta` token are not accepted. The form is parsed in an inert document, so its scripts never run.
5. When the form has a country select (`#GLUXCountryList`) that does not list the destination, the result is `NOT_OFFERED` and nothing is posted (amazon.com.au offers few countries). A form without a select (amazon.ca, amazon.com.mx) is posted to and its answer trusted.
6. It POSTs `/portal-migration/hz/glow/address-change?actionSource=glow` as JSON with the form token: `locationType: "COUNTRY"`, `district` and `countryCode` set to the destination, `storeContext` and `pageType` from the form URL, `deviceType: "web"` and `actionSource: "glow"`. Amazon answers a rejected token with 200 and an empty body, so only `successful: 1` with `address.countryCode` equal to the destination counts as `SET`. Anything else is `FAILED` with the reason.

After `SET` in the offscreen document, the page is downloaded again. After `SET` in a fallback tab, the worker closes that tab and opens the same URL in a fresh one, which carries the new location in the store's session; it does not reload the tab, so the next inspection cannot land in the document from before the change. A `FAILED` after a request in the offscreen document is redone once in a fallback tab (F3); a `FAILED` before any request is kept. Once a marketplace's location is `SET` or `ALREADY_SET`, every later page of it is downloaded with that destination expected, and one that shows another destination is read in a tab (F4). The result is kept in the run token, so each marketplace is set at most once per run and never tried again after a failure in a tab. In a tab, a timeout, or an injection whose result cannot be read, is `FAILED` and the read goes on in the same tab. Stop aborts the requests in the offscreen document and closes the tab, which ends the wait with the cancellation error. The setter's tab path also serves Chrome before 109, where every page is read in a tab.

**Side effects.** Target marketplaces are left delivering to the source destination; the previous location is never restored, and the user's own tabs on those stores show the new one after a reload. Only a country is set, never an address. The source marketplace is never a target, so its location is never changed. Two runs from sources with different destinations at once would switch each other's targets, and a page that then shows the other destination is reported as `DESTINATION_MISMATCH`, not priced; only a page whose destination cannot be read at all would be priced unchecked.

### Fallback tabs and robot checks

Every fallback tab goes through `readTempTab` in `orchestrator.ts`, which reads the page as soon as its document is ready instead of waiting for Chrome to report the tab `complete`. "Complete" means every image, ad and script of Amazon's page has loaded: a cold first tab reached it only after 18 to 20 seconds while `DOMContentLoaded` came at 6 to 9 seconds, and a search page reached it after 5 to 8 seconds against under 2. The extractors read only the HTML Amazon renders on its server, so the document is complete for them once it has been parsed.

Right after `chrome.tabs.create`, `waitForStorePage` injects `inspectPage` from `src/shared/robot-check.ts` with `chrome.scripting.executeScript` at its default timing. Chrome runs such an injection at `document_idle`, soon after `DOMContentLoaded`, in the document the tab ends up showing, after a redirect or a slow first byte too; `injectImmediately` is never used, because it runs while the body is still empty. The injection returns the page's address and whether it is a robot check. It is tried again, after 100 milliseconds and then twice as long each time up to one second, when Chrome:

- refuses it with "Cannot access contents of the page…" while the tab still reports `loading`, as it does while a new tab shows `about:blank` and while a navigation is on its way to the store;
- answers "Frame with ID 0 was removed.", when the document it was waiting for went away;
- comes back without a result, as it does when a navigation replaced the document or the load failed;
- or returns the address of a page on another host than the requested store's.

An error page ("Frame with ID 0 is showing error page") fails at once, as it did before: trying the injection again cannot turn it into the page. So does a refusal once the tab reports `complete`, which `chrome.tabs.get` tells without the `tabs` permission: Chrome then refuses only a page on a host the extension may not script, such as a store address that redirects to another host, and the read fails with that error, as it did when the worker waited for `complete`. The wait is limited to 20 seconds from the tab's creation; after that the read fails with "Timed out waiting for tab <id> to load". A tab that is closed while the worker waits, by Stop for example, ends the wait at once with "Tab <id> was closed before it finished loading", also when Chrome answers an injection or the status check with "No tab with id" before it reports the tab removed. The later injections of the location setter and the extractors run in the same document.

`inspectPage` is passed to `executeScript` as a function, which Chrome serialises from its source, so it uses nothing outside its own body and receives the markers (`ROBOT_CHECK_MARKERS`) as arguments. A page is a **robot check** when its path starts with `/errors/validateCaptcha`, `/errors_page/validateCaptcha` or `/checkpoint/` (amazon.com redirects to `/checkpoint/continue` after a burst of requests), when it has a form whose action contains `validateCaptcha` (Amazon serves its captcha with HTTP 200 at the address that was asked for, so the address alone does not show it; the captchas it serves with HTTP 503 carry the same form), or when its document came with HTTP 503. Amazon also turns requests away with an error page it serves with that status and no form ("Sorry! Something went wrong!" on amazon.com, "Tut uns Leid!" on amazon.de). `inspectPage` reads the status from the page's navigation timing entry (`performance.getEntriesByType("navigation")[0].responseStatus`); Chrome before version 109 reports none, and the page is then judged by the other markers. Amazon's "To discuss automated access to Amazon data please contact api-services-support@amazon.com" notice is not a marker: Amazon's not-found pages carry it too, with HTTP 404, and a store that answers the source ASIN with one is searched. `isRobotCheck` applies the same markers to an address, its HTML and, when it is known, its HTTP status. The offscreen document judges every download with it, by its final URL, HTML and status, and a robot check on a download is read once in a fallback tab (F1) before it can end the marketplace.

A robot check in a fallback tab ends the marketplace at once as `PARSE_FAILED` with the note "Amazon showed a robot check on <domain>", whichever page it was on: the ASIN lookup does not fall back to a search, a search match is not read, the variant check does not keep the listing it matched, and no other page of that marketplace is opened. The other marketplaces are still checked, however many have shown one: Amazon can challenge some stores while others load normally, and a marketplace gets no further request after its robot check. A run with a robot check is not written to the cache, so the next run checks every marketplace again. The page you are on is read as before, without an inspection.

### Other sellers' offers

A product page can show no price for the destination because its featured offer does not deliver there while other sellers' offers do. For LEGO 76417 with an address abroad, amazon.de, amazon.co.uk, amazon.fr, amazon.it, amazon.es and amazon.com.mx show a "See All Buying Options" button (`#buybox-see-all-buying-choices`) instead of a price; amazon.com, amazon.co.jp, amazon.ca and amazon.com.au show no such button. The product extractor, imported by the offscreen document or injected into a fallback tab, runs `extractProductDataWithOffers` in `product-extractor.ts`. The worker asks it for other offers (`readOtherOffers`) on every product read of a run, the run's baseline included, but not for `LOAD_SOURCE`, so opening the popup only reads the page you are on. When asked, and when the page gives no item price, quotes the source destination, does not say the item is currently unavailable and has that button, it:

1. Builds the request Amazon's All Offers Display sends when its "New" filter is ticked, from the data attributes of the page's `#all-offers-display-params` input, on the page's own origin: `GET /gp/product/ajax/aodAjaxMain/ref=aod_f_new?asin=<ASIN>&m=&qid=&smid=&sourcecustomerorglistid=&sourcecustomerorglistitemid=&sr=&pc=dp&pageno=1&filters=%257B%2522all%2522%253Atrue%252C%2522new%2522%253Atrue%257D`, where `filters` is `{"all":true,"new":true}` percent-encoded twice. Without the attributes it uses the page ASIN with every other value empty. `isonlyrenderofferlist=true` is never added: with it Amazon answers a bare fragment without `#aod-offer-list` or the counts.
2. Fetches it with the store's cookies: from a fallback tab as a same-origin request (`credentials: "same-origin"`), from the offscreen document through a fetch the page reader wraps to force `credentials: "include"`; the extractor itself is the same. In the offscreen document, a first request answered with a status that is not 2xx or with a robot check re-reads the product page in a tab (F5), and a refused later page keeps what was read. The whole read, every page included, has one 15-second deadline: page 1 gets all of it, each later page only what remains, no further page is asked for when less than 3 seconds remain, and what was read by then is used. The answer is the full panel as an HTML fragment, holding only new offers, with their number in `#aod-total-offer-count`; it is parsed in an inert document. While that total is above the offers read (or, when the panel gives no total, while its "See more" link `#aod-show-more-offers` is not hidden with `aod-hide` and its "End of results" `#aod-end-of-results` is not shown), it asks for `pageno=2`, then 3, with the same request, until it has read the total, a page adds no offer it has not seen (same seller, item and delivery), a page cannot be read, or three pages are in. Amazon's page size is unverified: no listing with more than one page of offers that deliver abroad was found.
3. Reads every offer of `#aod-offer-list` with `src/content/other-offers.ts`; the pinned block above the list (`#aod-pinned-offer`) is never read: it holds the featured offer, the one that does not deliver to the destination when the page shows no price (the captures read "No featured offers available"). Per offer: the condition (every offer of the filtered answer is new, and the check stays as a guard: new when Amazon's condition code, the offer's `amzn1.bot.NEW` content id, says so, whatever language the panel is in, or when the heading reads "New", "Neu", "Nuevo", "Neuf", "Nuovo" or "新品"), the price to pay (assembled from its visible symbol, whole and fraction, as its offscreen copy is blank, else the amount in its accessibility label; a list price is never read), the delivery price (the delivery message's `data-csa-c-delivery-price` attribute, else whichever comes first in the text of the primary or the no-promise delivery message, an amount or a "FREE" marker for zero, so a free-delivery threshold such as "FREE delivery on orders over €29" is never read as the charge), the seller and the dispatcher.
4. Lists every new offer of the pages read with both an item price and a delivery price (or free delivery) in `otherOffers`, in Amazon's own order ("sorted by price + delivery: low to high"), and quotes the first of them. The content script has no exchange rates, and an offer's item and delivery can be in different currencies, as on amazon.co.uk.
5. During a run, `normalizeResult` in the worker replaces that quote with the listed offer whose delivered total in the comparison currency is the lowest (`withCheapestOtherOffer` in `src/shared/comparison.ts`), keeping Amazon's order on a tie. Offers it cannot convert are left out of the choice; when none converts, Amazon's first offer stays. The goal is the cheapest delivered price, which Amazon's own sort does not promise. In the amazon.co.uk fixture, whose delivery prices are scrubbed, the second offer (£699.00 + CHF 40.86) is the cheaper one delivered, so a run quotes it.

A quote replaces the page's breakdown with that item and delivery, leaves the import fees unread, marks the listing available and sets `otherSeller` on the result: the seller, the dispatcher, whether Amazon dispatches it, how many new offers the panel lists (`offerCount`), how many were read (`readCount`) and whether that is all of them (`readComplete`), how many of those read deliver (`deliveringNewCount`), and how many new offers had an item or delivery price it could not read without saying they cannot ship (`unreadableCount`), so the popup claims "cheapest" only over the offers whose prices were read. After a short read, the popup's seller line counts only the offers read ("among the first 10 read of the 12 Amazon lists"). After the worker's choice, `otherSeller` describes the chosen offer and gains `comparedCount`, the number of listed offers whose delivered total could be converted, and the list of offers is dropped before the result reaches the popup or the cache. The popup claims "cheapest" only over the offers it compared. Its notes are "Quoted another seller's offer" and "Import fees not displayed for destination" instead of the page's missing price and shipping and Amazon's availability message. The orchestrator copies `otherSeller` and `otherOffers` into the `ComparisonResult` of an `OK` quote. For the baseline, `extractBaseline` returns the list beside the result, and the run hands it to `normalizeResult` only once the exchange rates are loaded, so the payload of a run that fails before then never carries it. When no offer read is quotable, the note is only "No other seller delivers the item new to the destination" when the read is complete and every new offer read either has a price and a delivery price or a delivery message that says it cannot be shipped there (amazon.com.mx's only offer "no se puede enviar"; the notices are the product page's undeliverable notices, shared in `price-reading.ts`). Otherwise it is "Other offers could not be read: …" with the reason: "listed N of M new offers" for a short read, "the panel gave no total" for a short read without a total, "a delivery price could not be read" for a delivery message that gives neither a price nor a reason it cannot ship, and "an item price could not be read". The claim is only made from complete evidence. A failed request, an error status, an answer without an offer list or a page that names no ASIN keeps the page's own reading and adds "Other offers could not be read: <reason>". The 15-second deadline keeps the read well inside the 25-second limit of a page job and the worker's 25-second wait for a fallback tab's extractor result, which remains a backstop for a script that never settles.

### Cancellation

**Stop checking** sends `CANCEL_COMPARISON {activeTabId}`. The background marks that tab's token as cancelled and aborts its controller, so the worker stops waiting for every page job of the run at once, also while the first offscreen document is still being created, whose job is then never sent. It sends `OFFSCREEN_CANCEL_RUN` with the run key once that creation has settled, or after 10 seconds when it has not: the document aborts every download of the run (pages, location requests and offers) and refuses later jobs of that key. It also closes the run's fallback tabs, including the tab of an ASIN lookup in progress. The run returns at once, throws "Comparison cancelled by user", and finishes with an error payload that the popup ignores because it has already returned to idle; lanes still running find the run cancelled and record nothing. A lookup interrupted by Stop never falls back to a search. Each run has its own token and key, so a run started right after Stop cannot un-cancel the previous one.

### Message correlation

Progress and result messages are broadcast with `chrome.runtime.sendMessage`, so every open extension page receives every message. Each one carries the `activeTabId` and `runId` from the request, and the popup's reducer (`belongsToRun` in `App.tsx`) only accepts a message when:

- its `activeTabId` matches the popup's tab, so a comparison running for another tab or window never shows up, and
- while a run is active, its `runId` matches the run this popup started, so late messages from a stopped or replaced run are dropped.

After a run finishes or is cancelled, further messages for it are ignored. Before the popup has started a run, it accepts progress for its own tab. That is how a reopened popup picks up a run that is still going.

The worker's messages to the offscreen document carry `target: "offscreen"`, and the popup ignores them. The document answers only `OFFSCREEN_PAGE_JOB` and `OFFSCREEN_CANCEL_RUN` and never answers any other message, so it cannot take a reply meant for the worker. It takes them only from the extension itself outside any tab (the sender's `id` is the extension's and it has no `tab`), so a content script in an Amazon tab cannot start or stop a job. Every message is serialised as JSON, so a page job's result holds only plain data.

### Why content scripts are IIFE-wrapped

`chrome.scripting.executeScript({ files })` runs a file as a classic script in the page's isolated world, and that world persists between injections. The same tab is injected several times: the source and product extractors run on the active tab for `LOAD_SOURCE` and again for every `RUN_COMPARISON`. A bundled file with top-level `const` or `let` bindings throws `Identifier '…' has already been declared` on the second injection.

The `isolateContentScripts` plugin in `vite.config.ts` wraps every chunk under `content/` in `(() => { … })();` at build time and shifts its source map by one line. It also fails the build if a content chunk imports or exports anything, because a classic script cannot. That is why each extractor keeps its own copy of small helpers such as price parsing, currency detection and the ASIN pattern. A module that only one content script imports is bundled into it: `price-reading.ts` and `other-offers.ts` are part of the product extractor. `tests/unit/build.test.ts` builds the extension and evaluates each extractor twice in the same JSDOM isolated world to prove it.

The offscreen document imports the content modules too, so it has its own build, `vite.offscreen.config.ts`, which writes `offscreen/offscreen.js` into `dist/` without emptying it. As a second entry of the main build, it would share chunks with the content scripts, which would then export symbols, and the plugin would fail the build. `pnpm build` runs both builds and copies the manifest; `public/offscreen.html` loads the bundle.

The background and the extractors exchange data through window properties in the isolated world: the worker writes a request such as `__ACROSS_AMAZON_SEARCH_REQUEST__`, injects the extractor file, then reads and deletes the result property (for example `__ACROSS_AMAZON_SEARCH_CANDIDATES__`). The location setter and the product extractor store a Promise in `__ACROSS_AMAZON_LOCATION_RESULT__` and `__ACROSS_AMAZON_PRODUCT_RESULT__`; `chrome.scripting.executeScript` waits for a Promise a function returns to settle, so the same read returns the settled `LocationResult` or `ProductExtractionResult`.

Everything lives in `chrome.storage.local`:

| Key | Contents | Lifetime |
| --- | --- | --- |
| `settings:v1` | Enabled marketplaces, comparison currency (`SOURCE` or a currency code) | Until changed |
| `cmp:<hash>` | Source, baseline, ranked results and FX table of a finished run | Reused for 30 minutes, deleted when read after that |
| `fx:YYYY-MM-DD` | The FX table for a UTC day | Reused for that day |
